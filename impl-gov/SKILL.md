# 实施治理

## 默认流程

1. 优先执行用户显式要求的评估、治理方式、恢复、验收或归档动作。
2. 当前上下文已有明确治理状态时直接沿用，不重新评估。
3. 状态不足时，从上下文已有的项目入口定位活动索引，只补读索引及匹配项指向的缺失状态；不要为获取已知路径重读 `AGENTS.md` 或目录规范。
4. 没有匹配状态且用户要求实施新变更时，读取 [治理粒度评估](references/assess.md)；仅解释、诊断或报告状态时不创建实施项。

多个活动项可能匹配时请用户指定，不逐份读取来猜测。已有判断只在用户要求重评、目标或范围实质变化、新的重要风险自然暴露，或状态明显失效时重新评估。

## 控制加载成本

按“当前上下文 → 缺失的项目入口或状态 → 当前动作所缺的参考规则”加载，信息足够即停止。当前上下文中的 `AGENTS.md` 声明、目录职责、已读场景和实施状态可直接使用；skill 触发、重复触发或阶段切换本身不构成重读理由。

入口不明时才补读 `AGENTS.md` 的相关部分；尚无声明且确需建立文档时，再按 [文档组织与常驻入口](references/documents.md) 落位。只知道场景入口不等于已知其内容，任务需要具体场景时仍应读取相关部分。上下文丢失、出现变更或冲突证据、用户要求核验时，只刷新受影响部分。不递归扫描仓库、不读取全部活动文档、不预加载完整治理规范。

## 基本约束

- 区分技术正确与产品语义正确，不猜测会改变业务含义的设计缺口。
- 控制当前范围，不顺手扩展相邻能力。
- 按实际影响选择最小充分验证，不机械运行全量测试。
- 给出命令或可执行指令时，优先使用平台无关的表达；只有无法避免时才提供 Linux shell 指令，并明确其适用环境。
- 涉及真实旧数据时先确认是否保留；未经用户确认，不实施迁移。
- 完整治理中，总体契约（`plan.md`）和当前阶段契约定稿后，自动委派 sub agent 做方向审查，并在契约内维护审查状态与意见；重点核对用户目的、领域设计和技术设计的核心意图，不作细节完备性检查。
- 完整治理中不得越过用户关或代替用户判定通过。
- 完整治理的工程关通过后，准备用户验收包仍是 Agent 的自动收尾工作；验收包未就绪前，不得请求用户签收、结束任务或把状态写为“等待用户验收”。
- 环境配置和数据准备是用户理解、复现及以后使用系统所需的知识；Agent 可以验证或执行准备，但不得让步骤对用户透明。
- 验收准备复用项目已经交付的入口、真实使用步骤和权威场景数据；不得为了补齐验收包新增仅供验收使用的代码、接口、脚本或测试替身。需要额外产品能力才能验收时，回到实施范围处理。
- 发现停止条件时暂停相关实施，不扩大错误基础。
