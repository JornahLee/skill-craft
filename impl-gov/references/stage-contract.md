# 阶段实施契约

仅在创建、修订或检查当前阶段契约时读取。

每阶段开始前形成可独立执行的契约，至少包含：

| 项目 | 要求 |
| --- | --- |
| 唯一用户结果 | 用一句话描述完成后用户能够做什么 |
| 用户场景 guideline | 使用项目已有的权威场景入口，可直接引用领域设计中的场景；只说明本阶段覆盖的用户目标、正向路径和依赖的可复用场景数据 |
| 设计依据 | 只引用本阶段依赖的已确认设计、ADR 和前置契约 |
| 实现语义映射 | 产品概念对应的代码对象、状态、入口和数据变化 |
| 范围与非目标 | 必须实现的能力和明确排除的相邻能力 |
| 固定验收数据 | 验收涉及数据时必须引用或给出具有明确业务语义的数据及准备步骤；优先引用用户场景 guideline 中已有的公共准备步骤，只记录本阶段新增或不同的数据 |
| 人工验收场景 | 从用户场景 guideline 选取本阶段路径；在此定义精确操作、异常／冲突边界和验收断言，不重写正常使用场景 |
| 用户验收包 | 工程关后由 Agent 自动补齐：用户可见的运行与环境准备、数据及准备步骤、精确输入、真实操作节点、逐步预期、语义判断点和反馈方式；未就绪前不得请求用户签收 |
| 自动化验证 | 迭代验证、收口验证及扩大条件 |
| 交付证据 | 运行方式、测试结果、界面证据、变更清单和限制 |
| 数据处理 | 真实旧数据保留需求及用户确认的处理策略 |
| 停止条件 | 必须暂停的设计缺口、语义冲突或范围冲突 |
| 验收结论 | 分别记录设计关、工程关和用户关结论 |

实现语义映射必须足以在编码前发现：

- 同一个词在产品设计和代码中是否表达不同对象。
- 状态或规则是否落在错误的数据粒度。
- 用户操作入口是否混合不同业务语义。
- 数据变化、历史留痕和界面反馈是否表达同一件事。
- 技术约束是否被误写成产品规则，或产品规则是否只存在于界面层。

## 设计关

开始编码前确认：

- 唯一用户结果、真实场景和依赖业务规则明确。
- 产品概念到实现对象的语义映射清晰。
- 范围、非目标、验收步骤和停止条件明确。
- Agent 无需猜测业务语义即可实施。

缺少上述任一项时，阶段不得标记为可执行。通过后更新阶段契约、总体计划和活动索引，再进入工程实施。

出现实现错误时留在当前阶段修复；出现设计缺口、概念映射错误或核心状态粒度错误时暂停，回到对应设计层级修订契约。新需求记录到后续阶段，不顺手加入当前阶段。

## 用户场景与验收的分工

- 用户场景 guideline 是项目中用户实际如何顺利完成目标的权威来源，可以位于领域设计或项目选择的其他位置。它维护目标、正常路径、可见正反馈、可复用的场景数据及跨功能依赖；不因某阶段的异常测试而膨胀为接口或测试脚本。
- 阶段契约引用该 guideline，并只补充本次改动的覆盖范围、精确输入、异常／冲突与工程验收断言。
- 工程关通过后，Agent 必须把选定路径转成可直接执行的用户验收包。用户不负责提醒或指挥这一步；验收包引用公共场景准备步骤，并补当前环境、本阶段数据和操作差异。环境与数据准备必须对用户可见，不得为补齐验收包开发专用代码或用测试替身代替真实使用路径。
