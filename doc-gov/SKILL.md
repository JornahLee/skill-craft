# 治理项目设计文档

让维护成本随本次影响范围增长，而不是随全部文档和代码数量增长。默认局部定位、渐进读取；不要为求稳妥直接扫描全部文档或代码。

## 维护四类知识

- **业务设计**：当前有效及已确认待生效的业务设计事实。按业务领域组织，定义概念、规则和流程。
- **技术设计**：当前有效及已确认待生效的技术设计事实。按技术模块组织，定义职责、边界、接口、数据和代码位置。
- **实施契约**：实施期过程记录。归档后允许过时，不作为当前业务或技术事实。
- **ADR**：重要决策的理由和历史。解释当前设计但不替代当前设计。

同一事实只能有一个权威定义。允许可追溯的非权威摘要、技术实现投影和历史记录。

## 先选择工作类型

1. **建立或重构文档体系**：完整读取 [model.md](references/model.md)，根据实际领域和模块建立地图与最小文档，不机械创建空文件。
2. **局部修改业务或技术设计**：从地图定位作用域，只读取目标文档、文件级上下游和必要的细节依赖。
3. **修改代码并同步文档**：从业务领域定位技术模块，再从模块文档的代码根目录、关键入口和测试位置开始读取代码。
4. **创建或推进实施契约**：使用 `$impl-gov`；不要在本 Skill 中重写或削弱其完整治理、阶段契约和三道验收关。
5. **记录重要决策**：按 [model.md](references/model.md) 的 ADR 条件和模板处理，同时更新受影响的当前设计。
6. **检查整个文档系统**：先读取 [audit.md](references/audit.md)。没有用户明确授权时，只能检测信号并建议全局审计。

## 执行局部治理

### 1. 定位作用域

按以下顺序渐进读取：

```text
业务地图
→ 相关业务领域
→ 关联技术模块
→ 模块代码根目录、关键入口和测试位置
→ 有证据表明相关时才沿依赖扩大
```

- 文件级关系直接读取双方维护的上游和下游列表。
- 细节级关系只沿依赖方的 Markdown 链接读取。
- 反向查找细节关系时，搜索目标文档路径或标题锚点；搜索结果不等于需要读取全部命中文档。
- 代码边界与实际导入、调用或数据流冲突时，指出映射漂移，不要静默扩大范围。

### 2. 检查文档复杂度与拆分

对本次需要实质修改的每份文档，先取得可量化的复杂度信号。任一信号达到下列预警线时，必须在写入前执行拆分检查；预警只触发检查，不直接决定拆分。

| 信号 | 预警线 |
| --- | ---: |
| 文档行数 | 500 行 |
| 文件大小 | 30 KB |
| 二级标题数 | 15 个 |
| 最大二级章节 | 200 行 |

使用 `wc -l -c` 获取行数和字节数，使用 `rg -n '^## '` 统计标题并计算章节长度。不要仅凭阅读感受判断文档是否过大。

命中预警后按以下顺序递进检查：

1. **识别结构上的内容群**：查找多个完整流程、状态机或生命周期，不同对象群，当前／待生效／历史内容混合，以及外部文档对不同章节的集中引用。
2. **判断语义边界**：确认候选内容群是否具有内聚主题或职责、稳定边界、独立变化原因和可独立验证的正确性条件。
3. **选择拆分形态**：根据知识类型决定建立父入口与子专题、拆成多个同级权威文档、拆成独立 ADR 或实施阶段，或将详情下沉而保留简短导航入口。
4. **验证拆分收益**：只在拆分能减少无关阅读、联动修改或状态混杂，且不会产生重复权威时拆分。若保持单文档，简要记录不拆的理由。

按文档类型优先选择自然拆分轴：

| 文档类型 | 优先拆分轴 | 常见结果 |
| --- | --- | --- |
| 业务设计 | 业务对象、规则集合、流程或子领域 | 领域入口与专题，或多个同级领域文档 |
| 技术设计 | 模块职责、能力、数据生命周期或处理机制 | 模块入口与专题，或多个同级模块文档 |
| ADR | 独立决策问题 | 多份 ADR 及其索引 |
| 实施契约 | 独立用户结果、阶段或交付边界 | 总计划与阶段契约 |
| 地图或入口 | 导航层级与详细定义 | 保留简短入口，将权威详情下沉 |
| 辅助或参考文档 | 使用任务、数据类别或操作流程 | README 或索引与按需读取的详情 |

父入口只维护整体目标、边界、子文档关系、稳定锚点和导航；子文档权威定义自身的对象、规则、接口、数据、流程和验证。每项事实只能存在于其中一处；父入口需要上下文时，只写明确标记并链接权威来源的非权威摘要。

不得按行数、字节数、固定章节数或章节序号直接切割。不得将一次实施阶段自动提升为长期专题，也不得新建继续指导当前实现的“历史设计”。过时过程归实施归档，重要决策理由归 ADR，当前设计只保留理解现状必需的简短背景。

### 3. 确认权威来源

写入前先判断内容属于哪里：

| 内容 | 权威位置 |
| --- | --- |
| 业务概念、规则、流程 | 对应业务领域文档 |
| 模块职责、接口、数据、代码边界 | 对应技术模块文档 |
| 一次实施的范围、阶段、进度和验收 | 活动实施契约 |
| 重要决策的背景、选择和后果 | ADR |

发现多个权威定义、归属不清或业务与技术语义冲突时暂停相关修改，列出冲突位置和需要用户决定的问题。不要自行选一个版本。

### 4. 修改最小充分内容

- 先修改权威来源，再处理受影响的摘要、实现投影和导航关系。
- 设计先于实现且尚未生效时，按 [model.md](references/model.md) 的“双态设计”在原权威位置同时维护当前有效设计和已确认的目标设计；不要把未决设想写入权威正文。
- 局部变化使用轻量双态标记，分别完整表达最小设计命题；相互关联的整段变化使用块级双态。按语义完整性选择，不按改动行数选择，也不使用删除线代替语义表达。
- 未标记内容始终表示当前有效设计。双态内容必须链接活动实施契约；实施任务、进度、迁移步骤和验证结果仍只写入契约。
- 新建文档前从地图、上游、下游和现有标题中查找已有归属。
- 已触发拆分检查时，按第 2 节确认的语义边界和拆分形态处理；未触发时仍可在有明确语义证据时主动建议拆分。
- 使用文档路径和标题锚点定位知识；不要自行引入独立 ID 系统。
- 复述其他文档的规则、条件、状态含义或数值时，使用 [model.md](references/model.md) 中的“非权威摘要”标记。
- 同一段落、表格或图中混合领域、技术和代码术语时，按 [model.md](references/model.md) 的“跨层术语标注”使用 `[领域]`、`[技术]` 和 `[代码:类型]` 前缀；单一层次的上下文不强制标注。

### 5. 同步关系

- 文件级上下游关系双向维护；新增、删除或改变关系时同步更新两端。
- 细节级依赖单向记录在依赖方，不创建反向副本。
- 技术模块声明它实现的业务领域或能力。
- 技术模块维护稳定代码锚点，不枚举普通内部文件。
- 实施契约列出受影响的业务文档、技术文档和代码模块。

### 6. 可视化复杂关系

当内容涉及三个及以上对象之间的关系、协作、依赖、流转或层级，或者涉及分支、循环、阶段、状态变化时，必须先用图表达整体关系。

按语义选择 Mermaid 关系图、流程图、时序图、状态图或层级图；简单字段和职责映射使用表格。图表达主关系，权威正文定义详细规则。

### 7. 完成检查

- 是否仍只有一个权威来源？
- 实质修改的文档是否已执行复杂度预警检查，并在命中时完成拆分判断？
- 拆分后是否仍能通过父入口或地图定位，且没有按篇幅机械切割？
- 文件级上下游是否双向一致？
- 非权威摘要是否标记并链接来源？
- 业务—技术—代码映射是否仍然正确？
- 跨层混合表达中的术语是否已显式标明层次？
- 当前事实是否误留在实施契约或 ADR 中？
- 双态设计是否只包含已确认目标，并能明确区分当前有效与目标待生效语义？
- 实施完成后是否按实际实现将双态收敛为单一当前设计并归档契约？
- 是否只检查了有证据支持的影响范围？

## 处理实施契约

将 `$impl-gov` 作为实施治理的唯一流程来源：

- 由它判断轻量实施或建议完整治理；完整治理仍须用户决定。
- 完整继承实施计划、阶段实施契约、设计关、工程关、用户关、验证粒度、偏差处理和完成门槛。
- 在本体系中只补充文档身份：活动契约在实施期间保持准确；归档契约是可能过时的历史记录。
- 契约完成前根据实际实现核对目标设计，将双态内容收敛为单一当前设计，并同步业务—技术—代码映射；实施终止时删除未生效的目标设计。

如果 `$impl-gov` 不可用，说明缺失，不要擅自发明一套同名的简化治理流程。

## 建议项目常驻约束

项目根 `AGENTS.md` 是本治理体系的常驻发现层；业务地图和技术地图是项目实际文档拓扑的权威来源；本 Skill 是触发后的操作规程。`AGENTS.md` 只记录治理体系的存在、实际入口和必须常驻的硬约束，不复制完整目录树。

当用户要求在项目中启用或更新本治理体系时：

1. 读取项目现有的根 `AGENTS.md`，保留所有无关指令。
2. 定位项目实际使用的业务地图、技术地图、ADR 目录、活动实施契约目录和归档实施契约目录；不要根据 [model.md](references/model.md) 的推荐骨架猜测路径。
3. 如果业务地图或技术地图尚不存在，先按 [model.md](references/model.md) 建立与项目相符的最小地图；不要创建没有实际内容的空目录或虚假入口。
4. 读取 [AGENTS.fragment.md](assets/AGENTS.fragment.md)，将其中全部路径占位符替换为项目实际路径，再根据现有 `AGENTS.md` 合并发现入口和硬约束。
5. 检查写入的文件和目录入口真实存在、指向当前权威地图，并确认没有遗留占位符。

未经用户要求，不修改项目常驻指令。只启用治理体系不等于获得全局审计授权。
