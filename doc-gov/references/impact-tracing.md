# 定位设计与代码影响

用于从设计文档定位代码，或从代码变更判断需要同步的设计文档。只定位有证据支持的直接影响，不执行全局审计。

## 从设计定位代码

先使用上下文已有的领域、模块与代码映射。以下仅表示关系链；只补读缺失环节，已知目标模块或代码锚点时不回头重读地图：

```text
业务地图与相关领域
→ 技术地图与关联模块
→ 模块声明的代码根目录、关键入口和测试位置
→ 实际导入、调用或数据流
```

模块文档只维护稳定代码锚点，不需要完整文件清单。从锚点开始搜索，只有发现明确依赖时才扩大代码范围。

## 从代码定位文档

1. 确定变更所属技术模块；优先使用模块文档声明的代码根目录和关键入口。
2. 读取该模块的业务映射、文件级上下游和任务直接命中的细节依赖。
3. 区分实现细节变化与长期设计事实变化。只有职责、边界、接口、数据、业务规则或稳定代码锚点变化时才更新设计文档。
4. 若影响多个模块，沿实际调用、导入或数据流逐项验证，不因“跨模块”直接扫描仓库。

## 处理漂移

- 代码越过文档声明边界时，报告设计—实现映射漂移。
- 文档映射与代码证据冲突时，不静默扩大模块范围；判断应修正文档、代码还是两者。
- 共享库和横切组件作为明确技术模块或依赖处理，不把它们作为全仓扫描理由。
- 无法从当前地图定位模块时，报告缺失入口；不要依据推荐目录猜测实际路径。

## 完成检查

- 每个影响判断是否有文档关系或代码依赖证据？
- 业务—技术—代码映射是否仍准确？
- 是否只同步了长期设计事实，而没有把普通内部实现写入设计文档？
- 是否明确报告了未验证范围和映射漂移？
