# 管理候选设计的生效性

只在需要记录已确认但尚未生效的候选设计，或明确使候选设计生效、撤销候选时读取。未决设想和备选方案不得进入受治理的设计文档。

## 权威性模型

在项目已声明纳入本治理的业务设计和技术设计范围内：

- 未声明生效性时，文档默认已经生效，是当前权威设计。
- 只有尚未生效的候选设计需要在 YAML frontmatter 中声明 `effective: false`；它不是当前权威来源。
- 禁止写入 `effective: true` 或扩展其他状态值。生效设计依靠缺省语义，不建立显式双态。

`effective: false` 只否定文档的当前权威性，不表示未完成、正在实施或处于任何工作阶段。设计是否生效与是否实现、测试、验收、合并或发布彼此独立；不得从一方推断另一方。

## 建立候选设计

- 保留当前权威文档不变，另建完整、自洽的候选文档并标注 `effective: false`。不得把当前权威文档整体改成未生效，导致当前设计失去权威来源。
- 候选设计只描述生效后应持续成立的业务或技术事实。范围、阶段、进度、任务、负责人、迁移步骤、完成比例、预计时间和验证结果属于活动实施契约，不得写入候选或当前权威设计。
- 决策背景、选择和后果写入 ADR。候选设计可以引用当前权威来源和相关 ADR，但不得复制其内容。
- 不使用 `[当前有效]`、`[目标·待生效]`、双态区块、删除线或文字差异在一份权威文档内混排当前设计与候选设计。

## 按任务使用

- 分析当前设计、修复当前缺陷或验证当前行为时，只把未标注 `effective: false` 的设计文档作为权威依据。
- 用户或活动实施契约明确指定某份候选设计为本次目标时，可以读取并据此实施；这不会使候选设计自动生效。
- 处理无关任务时，不得把候选设计当作约束，也不得假定它已经实现。

## 改变生效性

- 仅在明确要求保存候选设计时创建并标注 `effective: false`；仅在明确要求候选设计生效时移除该标记。不得给现有权威文档添加该标记，也不得依据设计成熟度、实施进度、验收结果、代码状态或 Agent 自身判断自动转换。
- 使候选设计生效时，将其作为新的完整权威设计，替换或取代原权威来源，更新受影响的地图、关系和引用，并移除 `effective: false`。生效动作本身不声明实现已经完成。
- 候选设计被放弃时，将其删除或归档并保持与当前入口隔离；不得因此修改现有权威设计。
