## 知识边界

- **业务设计**：当前有效及已确认待生效的业务事实。按业务领域组织，定义概念、规则和流程。
- **技术设计**：当前有效及已确认待生效的技术事实。按技术模块组织，定义职责、边界、接口、数据和代码位置。
- **实施契约**：实施期过程记录。归档后允许过时，不作为当前业务或技术事实。
- **ADR**：重要决策的理由和历史。解释当前设计但不替代当前设计。

同一事实只能有一个权威定义。允许可追溯的非权威摘要、技术实现投影和历史记录。

## 按任务读取

- **建立或重构设计体系**：完整读取 `model.md`，根据实际领域和模块建立地图与最小文档，不机械创建空文件。
- **局部修改业务或技术设计**：从地图定位作用域，只读取目标文档、文件级上下游和必要的细节依赖；按需读取 `model.md` 的对应章节。
- **修改代码并同步设计文档**：从业务领域定位技术模块，再从模块文档的代码根目录、关键入口和测试位置开始读取代码。
- **创建或推进实施契约**：使用 `$impl-gov`，不要在本 Skill 中重写或削弱其治理流程。
- **记录重要决策**：读取 `model.md` 的 ADR 章节，同时更新受影响的当前设计。
- **检查整个设计文档系统**：读取 `audit.md`。没有用户明确授权时，只检测信号并建议全局审计。

## 执行局部治理

### 定位作用域

按以下顺序渐进读取：

```text
业务地图
→ 相关业务领域
→ 关联技术模块
→ 模块代码根目录、关键入口和测试位置
→ 有证据表明相关时才沿依赖扩大
```

- 文件级关系直接读取双方维护的上游和下游列表。
- 细节级关系只沿依赖方的 Markdown 链接读取。
- 反向查找细节关系时，搜索目标路径或标题锚点；搜索结果不等于需要读取全部命中文档。
- 代码边界与实际导入、调用或数据流冲突时，指出映射漂移，不静默扩大范围。

### 检查复杂度与拆分

对本次需要实质修改的每份设计文档，先取得可量化信号。任一信号达到预警线时，在写入前执行拆分检查；预警只触发检查，不直接决定拆分。

| 信号 | 预警线 |
| --- | ---: |
| 文档行数 | 500 行 |
| 文件大小 | 30 KB |
| 二级标题数 | 15 个 |
| 最大二级章节 | 200 行 |

使用 `wc -l -c` 获取行数和字节数，使用 `rg -n '^## '` 统计标题并计算章节长度。命中后依次：

1. 识别完整流程、状态机、生命周期、对象群或状态混合等内容群。
2. 判断候选群是否具有内聚职责、稳定边界、独立变化原因和独立验证条件。
3. 按知识类型选择父入口与子专题、同级权威文档、ADR、实施阶段或详情下沉。
4. 只在能减少无关阅读、联动修改或状态混杂，且不产生重复权威时拆分。

不得按行数、字节数、章节序号机械切割。不得把一次实施阶段自动提升为长期专题。当前事实归设计文档，过时过程归实施归档，重要决策理由归 ADR。

### 确认权威来源

| 内容 | 权威位置 |
| --- | --- |
| 业务概念、规则、流程 | 对应业务领域文档 |
| 模块职责、接口、数据、代码边界 | 对应技术模块文档 |
| 一次实施的范围、阶段、进度和验收 | 活动实施契约 |
| 重要决策的背景、选择和后果 | ADR |

发现多个权威定义、归属不清或业务与技术语义冲突时，暂停相关修改，列出冲突位置和需要用户决定的问题，不自行选择版本。

### 修改最小充分内容

- 先修改权威来源，再处理受影响的摘要、实现投影和导航关系。
- 设计先于实现且尚未生效时，按 `model.md` 的双态设计在原权威位置维护当前有效和已确认目标；未决设想不进入权威正文。
- 新建文档前从地图、上下游和现有标题查找已有归属。
- 使用文档路径和标题锚点定位知识，不引入独立 ID 系统。
- 复述其他文档的规则、条件、状态含义或数值时，使用 `model.md` 的非权威摘要标记。
- 同一段落、表格或图中混合领域、技术和代码术语时，使用 `[领域]`、`[技术]` 和 `[代码:类型]` 前缀。

### 同步关系

- 文件级上下游关系双向维护；细节级依赖只在依赖方单向记录。
- 技术模块声明它实现的业务领域或能力。
- 技术模块维护稳定代码锚点，不枚举普通内部文件。
- 实施契约列出受影响的业务文档、技术文档和代码模块。

### 可视化复杂关系

涉及三个及以上对象的关系、协作、依赖、流转或层级，或者涉及分支、循环、阶段、状态变化时，先用合适的 Mermaid 图表达整体关系。简单字段和职责映射使用表格；图表达主关系，正文定义详细规则。

## 处理实施契约

将 `$impl-gov` 作为实施治理的唯一流程来源：

- 由它判断轻量实施或建议完整治理，并执行计划、阶段、验收、验证和偏差处理。
- 活动契约在实施期间保持准确；归档契约是可能过时的历史记录。
- 完成前根据实际实现核对目标设计，将双态收敛为单一当前设计，并同步业务—技术—代码映射；实施终止时删除未生效目标。

如果 `$impl-gov` 不可用，说明缺失，不擅自发明同名简化流程。

## 启用或更新常驻声明

1. 读取当前范围现有的 `AGENTS.md`，保留所有无关指令。
2. 定位实际业务地图、技术地图、ADR、活动契约和归档契约入口，不按推荐骨架猜测路径。
3. 缺少业务或技术地图时，按 `model.md` 建立与项目相符的最小地图，不创建空目录或虚假入口。
4. 读取 `assets/AGENTS.design.fragment.md`，替换实际路径后合并到 `AGENTS.md`。
5. 检查入口真实存在，没有遗留占位符或导航型旧约束。

切换治理类型时，替换完整的 `## 文档治理` 区块，不得叠加两个片段。未经用户要求，不修改常驻指令；启用治理不等于获得全局审计授权。

## 完成检查

- 是否仍只有一个权威来源？
- 实质修改的文档是否已检查复杂度并在命中预警时完成拆分判断？
- 文件级上下游是否双向一致，细节依赖是否保持单向？
- 非权威摘要是否标记并链接来源？
- 业务—技术—代码映射是否正确？
- 当前事实是否误留在实施契约或 ADR 中？
- 双态设计是否只包含已确认目标，并在实施结束时正确收敛？
- 是否只检查了有证据支持的影响范围？
