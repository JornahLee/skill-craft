# 局部维护设计文档

用于局部创建、修改、拆分或审查业务设计和技术设计。不要用本文件建立完整设计体系、分析代码影响或执行全局审计。

## 定位作用域

先复用上下文已有的目标、归属和关系。以下是缺失信息的定位路径，不是每次必须从头读取的步骤；目标已知时跳过地图，内容已知时跳过对应读取：

```text
相关地图
→ 目标业务领域或技术模块
→ 文件级上下游
→ 任务直接涉及的细节依赖
```

- 文件级关系读取双方维护的上游和下游列表。
- 细节级关系只沿依赖方的 Markdown 链接读取。
- 反向查找细节关系时搜索路径或标题锚点；搜索命中不等于需要读取全文。
- 新建文档前确认已有归属；上下文不足时才查相关地图、关系或标题。

## 确认权威来源

| 内容 | 权威位置 |
| --- | --- |
| 业务概念、规则和流程 | 对应业务领域文档 |
| 模块职责、接口、数据和代码边界 | 对应技术模块文档 |
| 一次实施的范围、阶段、进度和验收 | 活动实施契约 |
| 重要决策的背景、选择和后果 | ADR |

发现多个权威定义、归属不清或业务与技术语义冲突时，暂停相关修改并请求决定。

跨文档引用说明使用或依赖哪份文档、哪项职责，并链接对应正文；不以“非权威摘要”维护被引文档的第二份规则或状态说明。

依赖方自身新增的接入、组合或适用规则在依赖方正文定义。技术设计中的实现投影只定义本层职责、接口和数据契约，并链接业务来源，不重述业务条件或数值。

## 修改最小充分内容

- 先修改事实所属的权威正文；只有依赖方自身的设计事实改变时才更新依赖方正文。正文细节或状态变化不触发引用方同步；路径、职责或依赖关系变化时才更新受影响的导航与引用。
- 稳定入口变化时，按 [常驻治理声明](resident-config.md) 同步 `AGENTS.md` 对应条目，不重建其他导航。
- 需要表达已确认但尚未生效的设计时，读取 [设计生效性](design-state.md)，保留当前权威文档并另建带 `effective: false` 的候选设计。
- 同一段落、表格或图中混合领域、技术和代码术语时，使用 `[领域]`、`[技术]` 和 `[代码:类型]` 前缀。
- 文件级上下游关系双向维护；细节依赖只在依赖方单向维护。
- 技术模块链接其实现的业务领域或能力，不复制业务规则。

## 检查是否拆分

对本次需要实质修改的文档取得可量化信号。任一信号命中时执行拆分判断，不机械切割：

| 信号 | 预警线 |
| --- | ---: |
| 文档行数 | 500 行 |
| 文件大小 | 30 KB |
| 二级标题数 | 15 个 |

只有候选内容具有内聚职责、稳定边界、独立变化原因或独立验证条件，并且拆分能减少无关阅读、联动修改或状态混杂时才拆分。当前事实归设计文档，实施过程归实施契约，重要决策理由归 ADR。

## 表达复杂关系

涉及三个及以上对象的关系、协作、依赖、流转或层级，或者存在分支、循环、阶段和状态变化时，使用合适的 Mermaid 图先表达整体关系。简单字段和职责映射使用表格。图表达主关系，正文定义详细规则。

## 完成检查

- 是否仍只有一个权威来源？
- 是否只读取和修改了有证据支持的范围？
- 命中预警的文档是否完成拆分判断？
- 文件级关系是否双向一致，细节依赖是否保持单向？
- 地图与引用是否只保留定位和关系，未复述被引文档的细节或状态？
- 当前事实是否误留在实施契约或 ADR 中？
- 当前或候选设计是否混入了范围、阶段、进度、任务、迁移步骤或验证结果？
