## 整体模型

```mermaid
flowchart LR
    B["业务设计<br/>当前业务事实"] -->|"由谁实现"| T["技术设计<br/>当前技术事实"]
    T -->|"代码边界"| C["代码<br/>当前具体实现"]
    I["实施契约<br/>一次变化的记录"] -->|"改变"| B
    I -->|"改变"| T
    I -->|"最终修改"| C
    I -->|"产生重要决策"| A["ADR<br/>决策理由与历史"]
    A -->|"解释"| B
    A -->|"解释"| T
```

- 业务设计权威定义当前有效及已确认待生效的业务含义。
- 技术设计权威定义当前有效及已确认待生效的模块职责、边界和预期实现结构。
- 代码权威反映当前具体实现。代码与技术设计冲突时属于设计—实现漂移，需要显式处理。
- 实施契约记录变化过程，归档后允许过时。
- ADR 记录为什么决定，不替代当前设计；失效时由新 ADR 取代旧 ADR。

## 目录骨架

根据项目实际调整名称，不机械创建空目录：

```text
docs/
├─ business/
│  ├─ map.md
│  └─ <domain>.md
├─ technical/
│  ├─ map.md
│  └─ modules/
│     └─ <module>.md
├─ decisions/
│  └─ ADR-<number>-<title>.md
└─ implementation/
   ├─ active/
   └─ archive/
```

业务地图说明领域关系和配合；技术地图说明整体架构、模块关系及业务—技术映射。地图只做导航和概览，不复制详细规则。

目录骨架是推荐模型，不是项目实际路径的权威定义。项目可以根据现有结构调整名称和位置；Agent 不得依据该骨架猜测业务地图、技术地图、ADR 或实施契约的实际路径。

## 项目常驻入口

项目启用本治理体系后，在根 `AGENTS.md` 中维护一个精简的常驻发现入口。各层职责如下：

| 层次 | 职责 |
| --- | --- |
| 根 `AGENTS.md` | 声明采用设计型治理，列出业务地图、技术地图、ADR 和实施契约的实际入口，并提示何时使用 `$doc-gov` |
| 业务地图与技术地图 | 权威维护项目当前文档拓扑、领域与模块关系以及业务—技术映射 |
| `$doc-gov` | 定义触发后的定位、修改、关系维护、代码映射和审计规则 |

根 `AGENTS.md` 只维护稳定入口，不复制完整目录树、领域清单或模块清单。目录和关系发生变化时，先更新对应地图；只有稳定入口本身变化时，才同步更新 `AGENTS.md`。这样可以让 Agent 在尚未加载本 Skill 正文时发现治理体系，同时避免产生另一份项目拓扑事实源。

## 权威与重复

| 内容形态 | 规则 |
| --- | --- |
| 多处独立定义同一事实 | 禁止；合并到一个权威来源 |
| 为上下文复述事实 | 允许；标记非权威摘要并链接来源 |
| 业务规则的技术实现 | 允许；技术文档声明实现哪个业务设计 |
| 归档契约记录旧设计 | 允许；明确为历史，不据此判断现状 |

非权威摘要统一写成：

```markdown
> **非权威摘要**
>
> 本段仅为当前上下文提供说明。权威定义见：[目标文档](path#heading)。
```

普通链接没有复述事实时不需要标记。摘要不得引入来源中不存在的新含义。

## 双态设计

设计必须先于实现，但尚未实现的目标不能伪装成当前事实。设计文档可以在实施期间进入受控双态，同时权威定义：

- **当前有效设计**：系统当前实际遵循的设计。
- **目标待生效设计**：已经确认、实施验收后生效的设计。

双态记录设计状态，不记录变化过程。未决设想和备选方案不进入权威正文；决策理由写入 ADR，范围、阶段、进度、迁移步骤和验证结果写入活动实施契约。

```mermaid
stateDiagram-v2
    [*] --> 当前单态
    当前单态 --> 实施双态: 目标设计已确认
    实施双态 --> 当前单态: 实施终止，删除目标态
    实施双态 --> 新当前单态: 实施验收通过，删除旧态和标记
    新当前单态 --> 当前单态: 完成收敛
```

### 选择表达粒度

按能否完整表达目标语义选择形式，不按文字行数或差异大小选择：

| 变化范围 | 表达方式 |
| --- | --- |
| 少量独立设计命题即可完整说明 | 轻量双态标记 |
| 多条规则、流程、职责或模块关系必须组合才能成立 | 块级双态 |

如果 Agent 仍需在多处分散标记之间自行拼装目标状态，改用块级双态。双态以可独立判断真假的最小设计命题为单位；当前命题和目标命题都必须完整、自洽，不使用删除线或文字差异代替语义表达。

轻量双态示例：

```markdown
- [当前有效] 订单域根据订单状态判断是否允许取消，并在取消成立后通知库存域释放预占。
- [目标·待生效] 订单域只接收取消请求；履约域根据履约状态判断是否允许取消，并在取消成立后通知库存域释放预占。
```

块级双态示例：

```markdown
## 取消处理

> **迁移状态**
>
> 当前设计仍然生效；目标设计已经确认，验收后生效。
> 关联实施契约：[履约取消改造](../../implementation/active/example.md)

### 当前有效设计

完整描述当前规则、职责和协作关系。

### 目标设计｜验收后生效

完整、自洽地描述目标规则、职责和协作关系。
```

文档存在轻量双态但不适合在每处重复契约链接时，在文档开头统一声明迁移身份、标记含义和关联活动契约。未标记内容始终表示当前有效设计。

### 读取与收敛

- 分析现状、修复当前缺陷或验证当前行为时，只将当前有效设计作为现状依据。
- 实施关联目标时，同时读取当前有效设计、目标待生效设计和活动实施契约；目标设计定义最终语义，契约定义本次范围和实施过程。
- 处理无关功能时，不得假定目标设计已经实现；只有明确需要兼容已确认目标时才依赖目标态。
- 实施验收通过后，根据实际实现修正目标设计，删除旧态、迁移说明和双态标记，使目标态成为普通当前设计；同步业务—技术—代码映射后再归档契约。
- 实施终止时删除目标态，保留当前有效设计；不得让已结束实施的双态长期残留在权威文档中。

## 跨层术语标注

借鉴 C4 对元素类型和抽象层级显式标注的做法：同一段落、表格或图中混合多个层次时，为术语添加自解释前缀。

```text
[领域] 完整日记
→ [技术] RecallRecord
→ [代码:类] `SourceRecord`
→ [代码:表] `source_records`
```

- `[领域]`：业务领域设计中的概念、规则或行为。
- `[技术]`：技术设计中的角色、模型、模块、端口或机制。
- `[代码:类型]`：实际代码或存储制品；类型使用“类、协议、函数、模块、API、表、字段、索引”等具体名称。
- 单一层次的连续上下文可以省略前缀。跨层比较、映射，以及需要独立阅读的图和表必须保留前缀。
- 使用其他自定义标记时提供图例；不要使用未解释的 `D/T/C` 等缩写。

## 拆分规则

每条主线采用自己的最小模板，不使用万能模板。空的可选章节直接省略。

满足以下任一信号时考虑拆分：

- 内容拥有独立语义或职责；
- 内容有独立变化原因；
- 内容经常被单独引用；
- 内容能够独立理解和验收。

如果内容总是一起理解、一起变化，拆分只会增加跳转，则保留在同一文档。不要按字数、章节数量、代码文件数量或“看起来稳定”机械拆分。

## 关系规则

### 文件级关系

每份领域和模块文档维护双方一致的上下游：

```markdown
## 文档关系

### 上游文档

- [上游名称](../path.md)

### 下游文档

- [下游名称](../path.md)
```

文件级关系是有意保留的导航冗余。修改关系时同步更新两端。

### 细节级关系

在依赖方单向记录，不维护反向副本：

```markdown
## 关系

| 关系 | 目标 |
| --- | --- |
| 依赖 | [支付规则](../business/payment.md#支付完成) |
| 实现 | [退款能力](../business/refund.md#退款资格) |
```

使用文档路径和标题锚点，不分配独立 ID。移动或重命名文档时同步更新所有引用。

## 业务领域模板

```markdown
# 领域名称

## 范围

说明负责什么、不负责什么。

## 业务设计

按需要描述概念、规则和流程。

## 领域关系

说明依赖、协作，以及跨领域事实由谁权威定义。

## 文档关系

### 上游文档

### 下游文档
```

业务领域是拥有相对独立业务职责的范围，不等同于每一个代码实体。

## 技术模块模板

```markdown
# 模块名称

## 职责与边界

说明负责什么、不负责什么。

## 业务映射

链接本模块实现的业务领域或业务能力。

## 模块关系

说明依赖、对外能力和主要交互。

## 代码位置

- 根目录：
- 关键入口：
- 测试位置：

## 文档关系

### 上游文档

### 下游文档
```

技术文档描述值得长期维护的事实，不枚举可以直接从代码准确获得的普通内部细节。

## 代码映射

每个技术模块只维护稳定锚点：

- 模块代码根目录；
- 关键入口；
- 测试位置。

不要维护完整文件清单。Agent 从锚点开始搜索，只有发现明确导入、调用或数据依赖时才扩大代码范围。

共享库和横切组件应作为技术模块或明确依赖处理，不得成为默认扫描整个仓库的理由。实际代码越过声明边界时，报告映射漂移并判断应修正文档、代码还是两者。

## ADR

以下情况创建 ADR：

- 改变长期业务或技术边界；
- 影响多个领域或模块；
- 存在多个合理方案和重要取舍；
- 决策难以撤销或撤销成本高；
- 决策会约束后续设计。

普通、容易撤销的实现细节不创建 ADR。

最小模板：

```markdown
# ADR：决策名称

## 状态

提议 / 接受 / 已取代

## 背景

说明需要决定的问题和约束。

## 决策

说明选择及关键理由。

## 考虑过的方案

列出真正参与取舍的方案。

## 后果

说明收益、代价和长期约束。

## 影响范围

链接受影响的业务设计、技术设计和实施契约。

## 取代关系

需要时链接被取代或取代本记录的 ADR。
```

ADR 被取代时保留原文，创建新 ADR 并建立取代关系。当前业务或技术事实必须同步更新，不能只存在于 ADR。

## 可视化

当内容涉及三个及以上对象之间的关系、协作、依赖、流转或层级，或者涉及分支、循环、阶段、状态变化时，先用图表达整体关系。

| 内容 | 表达方式 |
| --- | --- |
| 静态对象、模块或文档关系 | Mermaid 关系图 |
| 操作步骤、判断和分支 | Mermaid 流程图 |
| 多对象按时间交互 | Mermaid 时序图 |
| 状态与状态转换 | Mermaid 状态图 |
| 上下级和包含关系 | Mermaid 层级图 |
| 简单字段或职责对应 | 表格 |

图必须能够独立看懂，使用明确节点名称。图表达主关系，正文定义详细规则；冲突时修正图，不将图变成另一个权威来源。
