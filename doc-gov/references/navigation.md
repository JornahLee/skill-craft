# 导航型治理

## 适用边界

只回答当前范围“有什么、在哪里、各自做什么”。目录或组件应能独立介绍，详细规则由各自入口权威定义，不需要维护跨目录依赖、协作、数据流、设计边界或修改影响关系。

项目级地图常驻根 `AGENTS.md`，说明主要目录或组件的职责、实际入口和读取时机。已有 README 可以承载面向人的介绍或更细导航，但不要求 Agent 为重获常驻地图而先读 README。目录内部规则由各自入口定义，不复制到常驻地图。目录之间没有关系时，不创建关系、不画关系图，也不引入业务地图、技术地图、上下游列表或代码映射。

导航型项目可以独立存在 ADR 或实施契约；它们的存在本身不触发设计型升级，也不要求建立业务地图或技术地图。

## 定位导航范围

- 先使用上下文已有的目录与职责；只对尚未明确或本次有变更证据的部分，检查局部目录与主要入口。不固定读取导航、顶层文件或全部目录说明。
- 优先从 `SKILL.md`、包清单或目录 README 的元数据和开头简介提取职责；证据不足时再渐进读取。
- 忽略构建产物、缓存、版本控制内部目录和无需用户发现的实现细节。
- 不读取目录内部全部文件来证明目录独立；没有关系需求和关系证据时，保持独立假设。

## 维护最小导航

只维护理解当前范围所需的最小内容：

- 项目或当前范围的用途；
- 主要目录或组件的路径；
- 每个入口一句清楚、不重叠的职责说明；
- 指向详细权威文档的链接。

导航中的目录用途由项目导航权威定义；目录内部行为、规则和流程由目录内文档权威定义。不要在导航中复述详细规则，也不要为没有关系的目录编造整体架构。

建立或调整上述稳定入口后，按 [常驻治理声明](resident-config.md) 将实际地图融入 `AGENTS.md`；只更新当前范围相关条目，保留其他 skill 的入口。普通查询直接使用已有地图，不触发目录建设。

## 判断升级证据

仅当当前治理范围内的证据同时具有以下性质时，才建议从导航型升级为设计型：

- **长期性**：当前实施结束后仍然成立；
- **结构性**：涉及职责边界、权威归属、依赖关系或影响范围；
- **必要性**：缺少设计文档会使 Agent 无法可靠定位事实或判断修改影响。

满足三项性质后，以下任一情况构成直接证据：

- 独立目录职责已经不足以表达长期真实边界；
- 跨目录长期事实缺少唯一权威来源；
- 稳定的跨目录影响关系无法从导航入口定位；
- 需要维护目录之外的第二个稳定知识维度及其映射，例如业务能力—技术模块或领域规则—代码位置。

目录数量、文档篇幅、局部内部复杂度、单个链接、单次跨目录修改、ADR 或实施归档的存在，都不能单独触发升级。优先在最小必要范围建立设计治理；一个目录内部复杂时，不自动升级整个仓库。

发现直接证据后只给出证据、建议范围和预期新增能力，等待用户确认，不自动重构。

## 完成检查

- 项目导航是否能回答“有什么、在哪里、各自做什么”？
- 需要用户发现的主要入口是否都有准确路径和职责？
- 路径与链接是否真实存在？
- 是否避免复制目录内部规则？
- 是否没有描述不存在的关系或引入无用设计结构？
