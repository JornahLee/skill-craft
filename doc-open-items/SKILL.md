# 标记文档待处理事项

使用统一语法记录尚未闭环的事项，使其可检索、可分类且可直接处理。

## 使用格式

严格写成：

```text
标记 :类目: 内容
```

- 标记、类目使用大写英文。
- 标记后保留一个空格；类目两侧使用半角冒号；第二个冒号后保留一个空格。
- 在 Markdown 文档中默认写成列表项：`- 标记 :类目: 内容`。
- 每个列表项只表达一个待处理事项。内容应具体说明缺口、问题、决策或风险，不写含糊的“后续处理”。
- 只标记真正未闭环的事项，不把普通说明、已确定结论或所有可能性都转成标记。

## 选择标记

| 标记 | 使用条件 |
| --- | --- |
| `TODO` | 已确认需要补充、实现或完成。 |
| `FIXME` | 当前内容已知不正确、相互矛盾或存在明显问题。 |
| `OPTIMIZE` | 有明确改进空间，但不阻塞当前阶段。 |
| `TBC` | 尚未确认，必须讨论、验证或取得信息后再决定。 |
| `RISK` | 存在潜在不利影响，需要评估、缓解或持续观察。 |
| `IDEA` | 仅为初步设想，尚未纳入正式内容或计划。 |

优先根据事项当前状态选择标记，而不是根据句子中出现的关键词选择。不要用 `TODO` 代替仍待决策的 `TBC`，也不要用 `RISK` 代替已经确定错误的 `FIXME`。

## 选择类目

| 类目 | 涵盖内容 |
| --- | --- |
| `ROADMAP` | 路线、阶段计划、当前重点。 |
| `SCOPE` | 范围、边界、做什么和不做什么。 |
| `RESP` | 职责、归属、参与方或模块之间的分工。 |
| `DESIGN` | 方案、结构、规则、组织或抽象方式。 |
| `FLOW` | 流程、机制、调用链路、状态流转。 |
| `DATA` | 数据来源、字段、口径、清洗、对齐、存储。 |
| `RISK` | 风险、约束、异常情况、需要观察的问题。 |
| `OPS` | 执行、维护、调度、配置、日志、监控。 |
| `DOC` | 文档缺口、说明不足、命名不清。 |

按事项主要影响的内容维度选择一个类目。不要因为标记是 `RISK` 就机械地选择 `:RISK:`；例如报表数据口径不一致应写为 `RISK :DATA:`。确实跨类目时拆成多个独立事项，或选择对后续处理最有帮助的主类目。

## 处理文档

1. 找出明确遗留项，以及由矛盾、缺失决策、未知条件或未覆盖异常暴露出的隐含遗留项。
2. 判断事项是已承诺、已知错误、非阻塞改进、待确认、潜在风险还是初步想法，并选择标记。
3. 按主要影响面选择类目。
4. 将内容改写为自包含、可行动或可验证的一句话；保留文档已有事实，不臆造负责人、期限或结论。
5. 把标记放在最相关段落附近；若用户只要求汇总，则集中列出并保留足够上下文。
6. 检查所有条目是否符合精确语法，并合并语义重复项。

若已有待处理项格式不统一，在不改变原意的前提下规范化。无法可靠判断状态或类目时，保留不确定性并向用户指出，不要默默猜测。

## 示例

```markdown
- TODO :DOC: 补充申请材料的提交方式与截止日期。
- RISK :DATA: 月报与财务系统采用的收入统计口径可能不一致，需要核对。
- TBC :ROADMAP: 是否先完成试点复盘，再扩大推广范围。
- FIXME :FLOW: 当前审批说明中的会签顺序前后矛盾，需要修正。
- OPTIMIZE :OPS: 后续可将人工汇总进度改为自动生成周报。
- IDEA :DESIGN: 考虑增加常见问题章节，暂不纳入当前版本。
```
